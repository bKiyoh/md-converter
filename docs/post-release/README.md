# リリース後文書ガイド

このディレクトリは、初回リリース後に判明した不具合、運用品質の改善、追加機能候補を
管理する。初回リリースまでの実装計画とは分離し、現在着手してよい作業を明確にする。

## 文書の役割

| 文書 | 役割 |
| --- | --- |
| [`maintenance-plan.md`](maintenance-plan.md) | リリース後の現行マイルストーン、修正候補、完了条件 |
| [`change-log.md`](change-log.md) | リリース後に実装・検証・公開が完了した変更の記録 |
| [`../plans/implementation-plan.md`](../plans/implementation-plan.md) | 初回リリース前の最終計画を保存する履歴 |
| [`../archive/implementation-plan-completed.md`](../archive/implementation-plan-completed.md) | 初回リリース前に完了したマイルストーンの履歴 |
| [`../incident/`](../incident/) | 発生した障害の事象、原因、対応、検証結果 |

製品動作の正本は引き続き `../specs/` に置く。このディレクトリの計画は作業範囲を
決めるものであり、現行仕様を上書きしない。

## リリース前後の境界

- `../plans/` は初回リリースまでに予定していた内容を保存し、リリース後の作業を追記しない
- `../post-release/` はリリース後に判明した問題と、今後の修正・改善だけを扱う
- 完了したリリース後マイルストーンは `../archive/` へ移し、現行計画へ残し続けない
- 公開済み変更の要約は `change-log.md` に追記し、未完了の予定と混在させない
- 実際に利用者へ影響した障害は、計画とは別に `../incident/` へ恒久的な記録を残す

リリース時点のGitタグやコミットが確定した場合は、境界の証跡としてこの文書へ追記する。
現時点では特定できていないため、日付やバージョンを推測して記録しない。

## 更新ルール

1. 1つのアクティブなマイルストーンだけを `maintenance-plan.md` で指定する
2. 既存仕様の不具合は、再現条件と回帰テストを定義してから修正する
3. 新しい製品判断が必要な項目は、対象仕様を先に更新する
4. 追加機能候補は、採用が決まるまでアクティブな対象範囲へ含めない
5. 修正後は自動検証と必要な手動確認の結果を記録する
6. 公開が完了した時点で `change-log.md` に利用者向けの変更内容を追記する
