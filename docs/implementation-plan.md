# Markdown変換エディタ MVP実装計画

## 0. この計画の前提と対象範囲

本計画は `AGENTS.md`、`docs/product-spec.md`、`docs/conversion-rules.md` と、2026-07-11時点のリポジトリ状態を基にする。MVPではMarkdown入力と変換をブラウザ内だけで完結させ、バックエンド、ユーザー登録、外部API連携、複数文書管理、高機能エディタなどの対象外機能は実装しない。

変換ルール文書には未定義の要素や、Slack・Backlogの公式仕様との照合が必要な記法が残っている。この計画ではそれらを推測で確定せず、「仕様上の要確認事項」として管理する。確認前に実装が必要になった場合は、マイルストーン開始時に仮定と影響範囲を提示してレビューを受ける。

## 1. 現在のリポジトリ構成

現時点ではVueアプリのソース、Vite設定、テスト、lint設定、依存パッケージはまだ存在しない。`README.md`、`package.json`、`docs/implementation-plan.md` は空であり、実質的には仕様策定段階である。

```text
md-converter/
├─ .vscode/
│  └─ settings.json          # Nuxtプロジェクトではないことを示すIDE設定
├─ docs/

```

Git上では上記ファイルがすべて未追跡で、コミット履歴も確認できない。Milestone 1では既存の仕様文書を保持したまま、Vue 3 + TypeScript + Viteの最小構成を追加する。

## 2. 採用する技術構成

| 分類 | 採用候補 | 用途・方針 |
| --- | --- | --- |
| UI | Vue 3 / Composition API | 画面と局所的な状態を管理する |
| 言語 | TypeScript | AST正規化、変換結果、警告を明示的に型付けする |
| ビルド | Vite | 開発サーバーと本番ビルドを提供する |
| Markdown解析 | `unified` + `remark-parse` + `remark-gfm` | Markdownをmdastへ解析し、GFMのテーブル・タスクリスト・打ち消し線を扱う |
| テスト | Vitest + Vue Test Utils | 変換ロジックの単体テストを中心に、必要最小限のコンポーネントテストを行う |
| 静的検査 | ESLint（Vue/TypeScript対応） | 型チェックとは別にコード品質を検査する |
| 型チェック | `vue-tsc` | `.vue` を含むTypeScriptの型を検査する |
| パッケージ管理 | npm | `package-lock.json` で依存を固定する |
| ブラウザ保存 | Web Storage API (`localStorage`) | 単一文書のMarkdown入力、テーマ選択、変換形式、表示設定を端末内に保存する |
| コピー | Clipboard API | ユーザー操作時に変換結果をコピーし、成功・失敗を通知する |

Pinia、Vue Router、UIコンポーネントライブラリ、CodeMirror、Monaco EditorはMVPでは導入しない。状態はルート画面とComposableで十分に管理できるためである。HTMLプレビューは既存のMarkdown解析結果から許可した要素だけをレンダリングし、生HTMLを破棄する。テキスト・属性をエスケープし、リンクURLのスキームを制限するため、HTMLサニタイザー依存は追加しない。

依存パッケージの正確なバージョンとNode.js対応範囲は、Milestone 1開始時に各パッケージの公式情報を確認して確定する。

## 3. Markdownパーサーの候補と選定理由

### 候補A：unified / remark（採用候補）

- `remark-parse` がMarkdownをmdastへ変換し、文字列置換ではなく構文木を基準に処理できる。
- `remark-gfm` により、MVP対象のテーブル、タスクリスト、打ち消し線を同じAST上で扱える。
- ブロック要素とインライン要素をノードとして区別でき、コードブロック内のMarkdown記号を誤変換しにくい。
- mdastの型情報を利用でき、アプリ用中間表現への変換境界を明確にできる。
- unifiedの出力プラグインを形式ごとに増やすのではなく、解析だけに利用する。これによりSlackやBacklog固有の変換方針をアプリ側で明示できる。

注意点は、`remark-gfm` を含む関連パッケージの構成とESM対応、改行ノードの扱い、CommonMark/GFMと各貼り付け先の差を事前に検証する必要があることである。

### 候補B：markdown-it

- CommonMark寄りのパーサーで、トークン列を取得でき、拡張も豊富である。
- 一方、MVPで必要な入れ子構造をアプリ用の木構造へ正規化する際、開始・終了トークンから階層を再構築する処理が必要になる。
- 今回は複数形式へ同一構造を変換するため、初めから木構造を得られるmdastの方がConverter間で共有しやすい。

### 候補C：micromarkを直接利用

- CommonMark/GFMの構文解析基盤として制御性は高い。
- ただし低レベルであり、MVPに必要なAST構築や変換処理の実装量が増える。独自Markdown方言を解析する要件もないため、現段階では過剰である。

以上から、Milestone 2で小さな技術検証を行った上で `unified` + `remark-parse` + `remark-gfm` を採用する。検証でMVP要素のASTが期待どおり得られない場合にだけ、markdown-itを再評価する。

## 4. Markdown入力から各形式への変換フロー

```text
textareaのMarkdown文字列
        │
        ▼
parseMarkdown(input)
  remark-parse + remark-gfm
        │ mdast
        ▼
normalizeMarkdownAst(tree)
  対応ノードをアプリ用中間表現へ変換
  未対応・不完全な構文を警告候補として収集
        │ MarkdownDocument
        ▼
選択中のConverter.convert(document)
  ├─ SlackConverter
  ├─ BacklogMarkdownConverter
  ├─ BacklogNotationConverter
  └─ PlainTextConverter
        │ ConversionResult
        ├─ output: string
        └─ warnings: ConversionWarning[]
        ▼
出力表示 / 警告表示 / クリップボードへのコピー
```

- 入力変更のたびに解析・変換する。MVPの単一textareaを前提とし、まず同期処理で実装する。
- パースに失敗して画面全体が停止しないよう、UI境界で例外を捕捉し、入力は保持したまま変換不能の警告を表示する。
- 入力の自動保存は変換フローと分離し、約500msのデバウンス後に元のMarkdown文字列を保存する。
- 変換形式を切り替えた場合は、既に正規化した文書を選択先Converterへ渡す。早すぎるキャッシュ最適化は行わず、性能上必要になった場合のみ `computed` で再計算範囲を制御する。
- 空文字は正常入力として扱い、空の出力と警告なしを返す。

## 5. ASTまたは中間表現の扱い

remarkのmdastをConverterへ直接公開せず、MVP要素だけを表すアプリ用の `MarkdownDocument` に一度正規化する。

理由は次のとおりである。

- パーサー固有の型や拡張ノードをConverterから隔離できる。
- GFMタスクリストなどのパーサー表現を一度だけ解釈し、全Converterで共通利用できる。
- 表現できない要素の警告規則を形式ごとに実装しやすい。
- Converterのテストではパーサーを通さず、必要な構造だけを組み立てて検証できる。

一方、将来要件を見越した汎用ASTは作らない。MVPで必要な最小限の型だけを定義する。

想定する概念は以下である。実際のTypeScript定義はMilestone 2でテストと共に確定する。

```ts
type MarkdownDocument = {
  blocks: BlockNode[]
}

type BlockNode =
  | HeadingNode
  | ParagraphNode
  | ListNode
  | QuoteNode
  | CodeBlockNode
  | TableNode
  | ThematicBreakNode

type InlineNode =
  | TextNode
  | StrongNode
  | EmphasisNode
  | DeleteNode
  | InlineCodeNode
  | LinkNode
  | LineBreakNode
```

補足方針：

- 見出しはレベルを保持する。
- 箇条書き・番号付きリストは `ordered`、開始番号、入れ子の項目を保持する。
- チェック状態はリスト項目の `checked: boolean | null` として保持する。
- コードブロックは本文と言語情報を保持し、子のMarkdownとして再解釈しない。
- テーブルはヘッダー、行、セル内のインライン要素、配置情報を必要な範囲で保持する。
- ソフト改行と明示的な改行を区別できる情報を保持する。最終的な出力規則は仕様確認後に決める。
- 位置情報は警告箇所の表示に必要な開始行・列へ絞って引き継ぐ。詳細なソースマップは作らない。
- パーサーが通常テキストとして解釈した不完全なMarkdownは、機械的に「不正」と断定できないため、警告対象にする条件をテストで限定する。

## 6. Converterのインターフェース

MVPではクラス階層やDIコンテナを導入せず、次の小さなインターフェースを満たすオブジェクトまたは関数群として形式ごとに実装する。

```ts
type OutputFormat =
  | 'slack'
  | 'backlog-markdown'
  | 'backlog-notation'
  | 'plain-text'

type WarningCode =
  | 'unsupported-node'
  | 'lossy-conversion'
  | 'invalid-structure'

type ConversionWarning = {
  code: WarningCode
  message: string
  location?: {
    line: number
    column: number
  }
}

type ConversionResult = {
  output: string
  warnings: ConversionWarning[]
}

interface Converter {
  readonly format: OutputFormat
  convert(document: MarkdownDocument): ConversionResult
}
```

- `convert` は同じ入力に対して同じ結果を返す副作用のない処理とする。
- ConverterはDOM、Vue、LocalStorage、Clipboard APIを参照しない。
- 警告は「出力先で表現を保持できず、情報が欠落または代替表現になる場合」を中心に返す。単なる形式変更をすべて警告にはしない。
- パース段階の警告と変換段階の警告はUI側で統合する。警告コードは実際に必要になったものだけを追加する。
- 変換形式の選択には `Record<OutputFormat, Converter>` 相当の単純なレジストリを使用し、プラグイン機構は作らない。

## 8. Vueコンポーネント構成

### `App.vue`

- Markdown入力、選択中の変換形式、正規化結果、変換結果を結び付ける。
- PCの2カラム配置と狭い画面の入力・出力タブ切り替えを管理する。
- ライト・ダークモードを適用し、選択をLocalStorageから復元する。切り替えは設定ポップオーバー内の太陽・月アイコンボタンで行う。
- 「Markdown Converter」の隣に情報アイコンを置き、タイトル、アプリの説明文、LocalStorageへの保存と外部送信を行わない旨は押下時のモーダル内に表示する。モーダル表示中の背面操作、Escapeキー、開閉時のフォーカスを管理する。
- 情報アイコンの右隣に設定ボタンを表示する。変換形式選択とコピーボタンはヘッダー右側に表示し、変換形式のラベルとセレクトは横並びにする。コピー状態と通知もここで管理する。
- 変換ロジックそのものは持たず、parserとConverterを呼び出す。

### `MarkdownEditor.vue`

- 通常の `textarea` と入力文字数を表示する。
- `v-model` 相当の値とイベントに加え、keydownを編集用Composableへ委譲し、保存処理は持たない。
- 太字・斜体・リンク、リスト入力の自動継続、Tabによる階層変更の文字列操作は純粋関数へ分離する。

### `OutputPanel.vue`

- Markdownプレビューと変換結果を切り替える内側タブを持つ。初期表示は変換結果とする。
- 各タブ内にはタブ名と重複する説明見出しを表示しない。
- 変換結果タブに読み取り専用の変換結果、出力文字数、警告一覧を表示する。
- 変換形式選択、コピー処理、通知はヘッダーを管理する `App.vue` に委ねる。

### `MarkdownPreview.vue`

- 既存のMarkdownパーサーと中間表現を利用してHTMLプレビューを表示する。
- 生HTMLは正規化時に破棄し、レンダラーが生成する許可済み要素だけを描画する。
- プレビューのレンダリング処理は純粋関数として単体テスト可能にする。

### `IconButton.vue` / `AppIcon.vue`

- テーマ切り替え、コピー、情報表示で共通するボタン構造と、依存を追加しないインラインSVGアイコンを提供する。
- 操作ごとの状態と処理は各利用元に残し、共通部品へ集約しない。

### `SettingsPopover.vue`

- 設定ボタン、ポップオーバー、テーマのアイコンボタン、エディター内部スクロールのスイッチを表示する。
- 外側クリックとEscapeキーによる閉じる操作を管理し、設定値そのものはpropsとemitで `App.vue` の既存状態へ接続する。

### `OutputFormatSelect.vue`

- MVPの4形式だけを選択肢として表示する。
- 表示名と内部IDの対応を一箇所で管理する。

### `ConversionWarnings.vue`

- `ConversionWarning[]` の総数をボタンへ表示し、同じ警告文は表示時にまとめる。
- ボタンを押したときだけ警告一覧を右ペイン内へ重ねて表示し、左右ペインの高さへ影響させない。
- 警告がない場合はボタンと一覧の領域を表示しない。

### `AppNotice.vue`

- コピー結果など短時間の通知を、通常の画面レイアウトに影響しない固定配置のトーストとして表示する。
- 汎用通知基盤にはせず、MVPで必要な表示だけを扱う。

コンポーネント分割は実装時の責務と規模を見て調整する。小さい部品を機械的に分割するのではなく、変換ロジックとブラウザAPIをUIから切り離すことを優先する。

## 9. LocalStorageへの保存方法

Markdown入力は `useMarkdownDraft`、テーマ選択は `useThemePreference`、変換形式は `useOutputFormatPreference`、エディター表示設定は `useAppSettings` Composableが読み書きを担当し、保存と例外処理は共通処理を利用する。

- 保存対象はMarkdown入力文字列1件、テーマ選択1件、変換形式1件、エディター内部スクロール設定1件とし、入力から再計算できる変換結果は保存しない。
- キーは `md-converter:draft:v1`、`md-converter:theme:v1`、`md-converter:output-format:v1`、`md-converter:settings:v1` とし、アプリ名、対象、スキーマ版を含める。
- 初期表示時に一度読み込み、Markdown入力が存在しない場合は空文字、テーマが存在しない場合または保存値が不正な場合はライトモード、変換形式が存在しない場合または保存値が不正な場合はSlack、エディター設定が存在しない場合または不正な場合は内部スクロールONを使用する。
- 入力またはテーマ変更後約500msでデバウンスして保存する。連続操作中の同期書き込みを減らす。
- 変換形式は操作頻度が低く、変更直後の再読み込みでも選択を失わないよう、変更時に即時保存する。
- エディター内部スクロール設定は変更時に即時保存し、JSONにはbooleanの `editorInternalScroll` だけを保持する。
- 空文字の扱いは「空文字を保存して再読み込み時も空にする」を基本案とする。キー削除と同等だが、初期サンプル文を将来導入しても削除状態を区別できるためである。初期サンプルはMVP計画には含めない。
- `localStorage` の利用不能、容量超過、セキュリティ例外を捕捉し、入力、設定変更、変換は継続する。保存失敗をユーザーへ通知するかは要確認とする。
- タイマーはコンポーネント破棄時に解除し、必要であれば未保存の最新値を同期保存する。この挙動は単体テストで固定する。
- 保存値は外部へ送信しない。テレメトリや外部フォントなど、入力漏えいにつながり得る外部通信もMVPでは追加しない。

## 10. 単体テストの方針

テストの中心はparser、AST正規化、各Converterとし、Vueコンポーネントではユーザー操作と表示の結線だけを確認する。

### parser・中間表現

- MVP対象の各Markdown要素が期待するノードになること
- 空文字、複数要素、ネストしたリスト、タスクリストを解析できること
- コードブロック内のMarkdown記号を子要素として解釈しないこと
- GFMテーブル（日本語、列幅の異なる文字列を含む）を保持すること
- ソフト改行、明示改行、段落間の空行を区別できること
- 不完全なMarkdownを例外で停止させず、パーサー結果に従って安全に扱うこと

### 各Converter

- `docs/conversion-rules.md` の確定済み例を表形式のテストケースにすること
- 空文字、単一要素、複数要素の組み合わせを確認すること
- 番号付き・箇条書き・チェックリストの入れ子と連続性を確認すること
- インライン装飾の入れ子、リンク内の装飾、コード内の記号を確認すること
- コードブロック、テーブル、水平線、日本語を確認すること
- 出力先で表現できない要素の代替出力と警告を確認すること
- 不完全な構文でも出力が欠落・クラッシュしないこと
- 改行コードをテスト環境に依存させず、出力方針どおりに統一すること

### Composable・UI

- Markdown入力とテーマのLocalStorageからの復元、500msデバウンス、保存失敗時の継続をfake timerとStorageのスタブで確認すること
- 変換形式の即時保存と復元、未保存・不正値・Storage例外時のSlackへのフォールバックを確認すること
- コピー成功・失敗のメッセージをClipboard APIのスタブで確認すること
- 変換形式の切り替え、文字数表示、警告表示を確認すること
- 狭い画面のタブはDOM上の状態とアクセシビリティ属性を確認し、見た目は手動確認すること
- Markdownショートカット、リスト入力の自動継続、単一・複数行のインデントは、文字列と選択範囲を入出力するUtilityの単体テストで確認すること
- Markdownプレビュー／変換結果タブ、入力・形式選択の状態維持、プレビュー反映、およびヘッダーの形式選択とコピー表示はコンポーネントテストで確認すること

## 12. 技術的なリスク

| リスク | 影響 | 対応方針 |
| --- | --- | --- |
| Slack/Backlogの実際の貼り付け解釈と文書化された記法に差がある | 貼り付け後の表示が期待と異なる | 各Converter着手前に公式仕様を確認し、可能なら対象サービス上で代表ケースを手動検証する |
| CommonMark/GFMと入力者が想定するMarkdownに差がある | 不完全な記法や改行の解釈が異なる | 採用方言をGFMベースと明記し、曖昧ケースをfixture化する |
| mdastから中間表現への正規化で情報を落とす | 後段Converterで正しく出力できない | MVP要素ごとのparserテストを先に作り、位置・改行・リスト情報を必要最小限保持する |
| ネストしたインライン装飾が出力先で表現できない | 記号の衝突や情報損失が起きる | ノードを再帰的に描画し、出力先の制約に応じて警告と安全な代替表現を返す |
| Slack向けテーブルの等幅整形で日本語の表示幅がずれる | コードブロック内の列が揃わない | 文字数と表示幅を混同せず、全角・絵文字の扱いを仕様確認する。必要性が確定するまで幅計算依存は追加しない |
| リアルタイム解析の負荷が大きい入力でUIが遅延する | 入力体験が悪化する | MVPでは同期処理を計測し、問題が確認された場合のみ変換デバウンスや入力上限を検討する。Workerは先行導入しない |
| LocalStorageやClipboard APIが利用できない | 保存・コピーに失敗する | 例外を捕捉し、編集と手動コピーを継続できるメッセージを表示する |
| ブラウザ・OSで改行やClipboard挙動が異なる | 貼り付け結果が不一致になる | 内部改行を統一し、対象ブラウザ範囲を決めて手動確認する |
| 保存されたテーマ値が不正または旧形式である | 意図しないテーマで表示される | `dark` と `light` だけを受け入れ、それ以外はライトモードへフォールバックする |
| 保存された変換形式が不正または廃止済みである | 対応するConverterを取得できない | 共通の形式ID一覧で保存値を検証し、不正値はSlackへフォールバックする |
| パーサー関連依存のESM/Node対応条件 | テスト・ビルド構成が衝突する | Milestone 1/2で公式の対応条件と最小構成を検証し、lockfileで固定する |

## 13. 仕様上の要確認事項

以下は実装前にプロダクト判断または公式仕様・実環境での確認が必要な事項である。解決済みの項目は、確定した方針と参照先を記録する。

### 変換仕様

1. `docs/conversion-rules.md` にない見出し2〜6、段落、箇条書き、番号付きリスト、ネスト、コードブロック、テーブル（Slack以外）、改行の各形式での正確な出力。
2. Slackの対象がメッセージ作成欄への貼り付け用テキストか、APIの `mrkdwn` か。MVPはAPI連携対象外だが、両者の解釈差を混同しない必要がある。
3. Slackの見出し代替、番号付き・ネストリスト、チェック記号、水平線、コードフェンス、リンク構文が現在の公式クライアントで意図どおり扱われるか。
4. Slackテーブルをコードブロック化する際、列をパイプ区切りのまま残すか、表示幅を揃えるか、ヘッダー区切り行を残すか。
5. Backlog MarkdownとBacklog記法それぞれで有効な、見出しレベル、装飾、タスクリスト、引用、コードブロック、リンク、テーブル、水平線、改行の公式記法。
6. Backlogのプロジェクト設定や入力欄によって記法モード・対応要素が異なる場合、どの利用条件を対象とするか。
7. 出力先で直接表現できない「装飾の入れ子」「表内の複数段落や改行」「リスト内コードブロック」などの代替表現と警告要否。
8. （Milestone 6で解決済み、変換規則改定済み）プレーンテキストでは、見出しレベル1を `【見出し文字列】`、レベル2を `■ 見出し文字列`、レベル3を `▼ 見出し文字列`、レベル4〜6を `● 見出し文字列` で表す。レベル4〜6だけは階層の統合を警告する。コードブロックは各行4スペースの字下げ、データ行がある2列テーブルは `項目：値`、データ行がない2列テーブルと3列以上のテーブルはヘッダーを含むタブ区切りで表す。詳細は `docs/conversion-rules.md` の「プレーンテキスト変換の対象と補足」に従う。
9. （Milestone 6のプレーンテキストについて解決済み）ソフト改行と明示的な改行はいずれも改行文字として保持し、段落などのブロック間は空行で区切る。他形式の確定済み規則は `docs/conversion-rules.md` の各節に従う。
10. 不完全なMarkdownをどの範囲で警告するか。CommonMark上は通常テキストになる入力を一律にエラー扱いしない方針でよいか。
11. （Milestone 6のプレーンテキストについて解決済み、変換規則改定済み）警告は情報が実際に欠落する場合だけ返す。同一種類の情報損失は、レベル4〜6の見出し、リンク、チェック項目、コードブロック、テーブルの各出現単位で返し、レベル1〜3の見出し、通常の装飾除去、リスト記号の統一、水平線の代替表現、空行の正規化には返さない。詳細は `docs/conversion-rules.md` に従う。

### UI・保存仕様

12. （Milestone 13で更新済み）初期選択はSlackとする。選択した変換形式は `md-converter:output-format:v1` へ即時保存して再読み込み時に復元し、未保存・不正値・Storage例外時はSlackへフォールバックする。
13. （Milestone 7で解決済み）文字数はUnicodeコードポイント数で数える。UTF-16コード単位ではサロゲートペアを2文字と数えるため、画面上の文字数として採用しない。結合文字や絵文字シーケンスを1文字にまとめる書記素単位の計数は、対応ブラウザが未確定のためMVPでは導入しない。
14. （UI簡素化で更新済み）全削除ボタンは提供しない。
15. （Milestone 8で更新済み）ライト・ダークモードは手動切替とし、選択を `md-converter:theme:v1` へ保存する。保存値がない場合または不正な場合はライトモードを使用する。
16. （Milestone 8で解決済み）LocalStorageへの保存失敗は通知を追加せず、画面上の入力と変換を継続する。保存失敗時の通知文言がプロダクト仕様に定められておらず、コピー通知と誤認させないためである。
17. （Milestone 9で解決済み）767px以下を狭い画面とし、初期タブは入力とする。入力中に表示が意図せず切り替わらないよう、変換後も出力タブへ自動移動しない。タブは左右矢印、Home、Endキーで操作できるようにする。
18. （Milestone 9時点の既知の制約）対応ブラウザの正式な範囲は未確定である。Clipboard API、LocalStorage、CSS Gridおよび標準的なタブ操作を利用できるブラウザを前提とし、対象ブラウザ決定後に実機確認する。
19. （Milestone 10で解決済み）右ペイン内タブの初期表示は変換結果とする。外側の狭い画面向けタブは入力／右ペインの切り替えとして維持し、初期表示は入力のままとする。
20. （Milestone 10で解決済み）選択文字列からリンクを挿入した場合は `URL` を選択する。選択がない場合は `[](URL)` のリンクテキスト位置へカーソルを置く。
21. （Milestone 10で解決済み）プレビューでは生HTMLノードを破棄し、レンダラーが許可したHTMLだけを生成する。リンクは相対URL、フラグメント、`http`、`https`、`mailto`、`tel` だけを有効にする。

## Milestone 1で実施する具体的な作業

次回Milestone 1を開始する場合は、次の順序で進める。

1. Node.js/npmの対象バージョンと、Vue/Vite/Vitest/ESLint/vue-tscの公式な互換条件を確認する。
2. 既存ファイルを保持したまま、Vite + Vue 3 + TypeScriptの最小ファイル群を作成する。
3. `package.json` に開発、ビルド、テスト、lint、型チェックのscriptsと必要最小限の依存を定義し、lockfileを生成する。
4. TypeScript、Vite、Vitest、ESLintの最小設定を追加する。
5. `main.ts`、最小の `App.vue`、グローバルスタイル、`index.html` を追加する。変換UIはまだ作らない。
6. テスト基盤確認用の小さなサンプルテストを追加する。
7. READMEに必要環境、セットアップ、各検証コマンドを記載する。
8. 開発表示を手動確認し、lint、型チェック、単体テスト、本番ビルドを実行して結果を報告する。

Milestone 1ではMarkdownパーサーをまだ追加せず、パーサー導入と中間表現はMilestone 2に限定する。
