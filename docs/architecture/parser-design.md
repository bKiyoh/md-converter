# Markdownパーサー設計

> 文書区分：現行設計。文書の役割と読む順番は
> [`docs/README.md`](../README.md) を参照してください。

## 採用結果

Markdown解析には `unified`、`remark-parse`、`remark-gfm` を採用する。文字列置換ではなくmdastを経由でき、GFMのテーブル、タスクリスト、打ち消し線を同じ構文木として扱えるためである。正確なバージョンは `package-lock.json` を正とする。

mdastはConverterへ直接渡さない。`src/parser/normalizeMarkdownAst.ts` でアプリ用の `MarkdownDocument` へ正規化し、パーサー依存をこの境界に閉じ込める。

## 保持する構文情報

- 見出しレベル、段落、引用、水平線
- 太字、斜体、打ち消し線、インラインコード、リンク
- リストの順序種別、開始番号、疎密、入れ子、チェック状態
- コードブロックの本文、言語、メタ情報
- テーブルのヘッダー、行、セル内インライン要素、列配置
- ソフト改行と明示的な改行の区別
- 生HTMLの元文字列
- 警告位置に利用する開始行・列

参照形式のリンクは文書内の定義と解決し、通常のリンクノードへ正規化する。定義自体は出力対象のブロックには含めない。

## 既知の制約

- 入力方言はCommonMarkを基礎としたGFMとし、他のMarkdown方言固有の構文は解釈しない。
- 生HTMLはHTMLとして解釈せず、元文字列と位置情報を専用ノードへ保持する。出力と警告の扱いは `../specs/conversion-rules.md` に従う。
- 画像と脚注は対応範囲外であり、中間表現には定義しない。対応する場合は、先に仕様と実装計画を更新する。
- CommonMark/GFMが通常テキストとして受理する不完全な記法は、推測でエラーや警告にせず、元の文字をテキストノードとして保持する。
- テーブルセルの複数ブロックやHTMLの `<br>` など、GFMテーブルで直接表現されない構造は保持対象外とする。
- ソフト改行と明示的な改行は構文上区別して保持し、出力方法は各Converterの仕様に従う。
