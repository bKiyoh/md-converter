# No.2 フォントの最適化 設計書

作成日：2026-10-15／優先度：高／状態：PR-11で比較・採用・対象実装と開発環境の検証済み（実機検証は残件）

## 1. 目的と対象範囲

日本語の長文を読み書きしやすい本文フォントを選ぶ。フォーカスモードのtextareaと
検索ハイライト層だけを対象にし、通常モードの等幅フォント、タブ名、コードプレビューの
書体は維持する。サイズはNo.3、行間・字間はNo.4で決める。

## 2. 変更前の状態

`src/style.css` のtextareaと検索ハイライト層は、いずれも
`"SFMono-Regular", Consolas, "Liberation Mono", monospace`、`0.95rem`、行高1.65。
日本語の具体的な表示書体はOSとフォールバックに依存する。変更前の現行仕様には本文用の
日本語フォント指定はない。

## 3. 比較案と推奨案

| 案 | 利点 | 制約 | 判断 |
| --- | --- | --- | --- |
| 現行の等幅スタック | コードや表の空白配置を読み取りやすい | 日本語本文の書体が環境に依存する | 比較基準 |
| 日本語システムフォント | フォント資産の追加が不要 | OS間で字形と折り返しが異なる | 比較対象・フォールバック |
| Noto Sans JPを同一オリジン配信 | 本文の書体を揃えやすい | 配信容量、ライセンス表示、読込時の再配置が必要 | 比較後に採用 |

Noto Sans JPの400を第一候補とし、既存フォントとの比較後に採用を確定した（第8章）。
ブラウザに同名フォントが入っていることだけを前提とする方式は、比較の再現性がないため採用しない。
外部のGoogle Fonts CSS/CDNは使用せず、配布フォントをリポジトリへ同梱する。

採用したフォールバック順は以下とする。これは本アプリ向けの選定であり、参考サイトの指定値ではない。

```css
font-family: "Noto Sans JP", "Hiragino Kaku Gothic ProN", "Yu Gothic", Meiryo, sans-serif;
font-weight: 400;
```

等幅から変更すると、入力中のMarkdown表やコードの空白による見かけの位置合わせは変わる。
textarea内のコード部分だけ別書体にする機能は追加しない。原文の空白やタブ文字は維持し、
比較ではコード・表の構造記号と文字を読めることを確認した。通常モードでは従来の等幅編集を利用できる。

## 4. フォント資産と読込設計

- Noto Sans JP 2.004の公式可変TTFを400へ固定したWOFF2を採用する。文字サブセットは削除せず、16,732コードポイントを維持する。配布版とハッシュは資産記録へ固定した。
- 自己ホスト可能な配布物を選び、動的サブセット生成や外部APIは導入しない。
- `public/fonts/` へ資産とライセンスを置き、Viteの配信baseに追従するURLで参照する。
- `@font-face` は400だけを宣言し、`font-display: swap` を使用する。preloadやlocal()は指定せず、フォーカス本文で必要になった時に同梱ファイルを読み込む。
- 読込失敗中もフォールバックで編集を続けられるようにする。本文を隠して読込を待たない。
- 本文に応じた外部URL要求を発生させない。新規npmパッケージは追加しない。
- 静的フォントを追加した場合、配布物に付属するライセンスと著作権表示を保持し、
  `THIRD_PARTY_NOTICES.md` の生成運用を確認して静的資産の表示を消さない配置にする。
- `docs/release/asset-provenance.md` に出典、配布版、対象ファイル、ハッシュを記録する。

Notoの公式資料はNoto Sans JPを日本語向けの系列として説明している。
同梱ファイルは公式配布物のOFL 1.1を確認し、付属ライセンス全文を保持した。
出典：[Noto公式の利用ガイド](https://github.com/notofonts/noto-docs/blob/main/docs/website/use.md)。

## 5. 実装設計と影響

- フォーカスモード用の書体・太さをCSS変数にし、textareaと検索ハイライト層で共有する。
- `document.fonts` の `loadingdone` / `loadingerror` で、フォーカスモード中だけ既存検索位置とスクロールを再評価する。入力値・選択・フォーカスは更新しない。両リスナーは破棄時に解除する。
- No.6を実装する場合は、同じタイミングでカーソル計測キャッシュを破棄する。
- 通常モードのスクロール同期は実際のcomputed styleを計測する既存設計を維持する。
- モード変更でtextareaを再生成せず、既存の位置復元とUndo/Redoを維持する。

| 変更ファイル | 内容 |
| --- | --- |
| `src/style.css` | フォント宣言、フォーカス用変数、検索層との共有 |
| `public/fonts/` | 400のフォント資産、付属ライセンス全文、出典案内 |
| `src/components/editor/MarkdownEditor.vue` | 読込完了・失敗後の検索位置再評価と破棄時の解除 |
| `docs/release/asset-provenance.md`、`THIRD_PARTY_NOTICES.md`、`scripts/generate-third-party-notices.mjs` | 資産の出典、再現手順と生成後も維持する配布表示 |
| `docs/specs/focus-mode-spec.md` | 採用書体、対象、フォールバック方針 |

## 6. 比較・検証と受け入れ条件

1. 同じ本文幅・サイズ・行間で、現行等幅、日本語システム書体、Noto Sans JPを比較する。
2. 日本語長文、句読点、英数字、`0/O`、`1/l`、全半角記号、絵文字、コード、表を確認する。
3. ライト・ダークの双方で400の読みやすさ、プレースホルダー、選択、検索表示を確認する。
4. macOS、Windows、iPadOSを含む対象ブラウザで、表示書体・OS・版を記録する。
5. キャッシュあり／なし、通信失敗で欠字や入力不能がなく、読込前後で検索層がずれない。
6. 配信ファイルの実容量と読込時間を記録する。容量に見合う改善が確認できない場合は追加しない。
7. 200%ズーム、日本語IME、Undo/Redo、モード往復の編集位置を確認する。

見た目だけを固定する単体テストは追加しない。読込イベント処理を追加する場合は、破棄時の
解除と検索状態の維持を対象にテストする。実装時はlint、型チェック、テスト、ビルドを行う。

## 7. 採用工程と参考資料

PR-11では比較工程を現行仕様と実装計画へ先に定義した。No.1適用後の条件で比較し、
採用を確定して両文書を更新してから本体へ適用した。No.3・4の実装時には文字組みの
組み合わせを再確認する。今回はサイズ・行間・字間を変更していない。

利用者指定の[参考サイト](https://mount.jp/magazine/monex-dev-with-ai/)は2026-10-15の調査で
本文・CSSを取得できず、実際のフォントを未確認。Noto Sans JPを使用しているとは断定しない。

## 8. 比較結果と採用理由（2026-10-15）

macOS 14.5 arm64で、Chromium 148.0.7778.96、Firefox 150.0.2、Playwright WebKit 26.4を使用。
本文幅720px、サイズ0.95rem（既定の16px基準で15.2px）、行高1.65、字間normal、太さ400を
固定し、同じ日本語長文・句読点・英数字・全半角記号・絵文字・異体字・コード・表・リストを入力した。
各画像は実アプリのtextareaを同じ条件で撮影して並べたもの。読みやすさは開発環境での目視評価であり、
読み書き速度や疲労の改善を実測したものではない。

- [ライト比較（左から等幅、システム、Noto）](assets/no-02-font-comparison-light.png)
- [ダーク比較（同順）](assets/no-02-font-comparison-dark.png)

| 観点 | 等幅 | 日本語システム | Noto Sans JP 400 |
| --- | --- | --- | --- |
| 日本語・英数字の見え方 | 本文と英数字で字形・太さの印象が異なる | 本文に適するがOS依存 | 日本語と英数字の見え方が揃う |
| 英数字の幅 | 同幅 | プロポーショナル | プロポーショナル |
| コード・表 | 空白の並びを追いやすい | 列の見かけの位置が変わる | 列の見かけの位置が変わるが文字と構造を読める |
| 配信量 | 追加なし | 追加なし | 初回に2,302,780 bytes、フォーカス時のみ |
| OS間の書体 | 環境依存 | 環境依存 | 同梱書体を共有、未対応文字・絵文字はOSへ委ねる |

ChromiumのCanvas計測では `iiii` / `WWWW` は等幅で約36.49 / 36.49px、
システムで約14.47 / 61.16px、Notoで約16.72 / 53.38px。コードの整列への影響を明示したうえで、
本文の字形を揃えられるNotoを採用した。分割ファイルや文字範囲の保守を増やさず、400の1ファイルを
必要時に読み込み、再訪時はブラウザのキャッシュへ委ねることで、約2.20MiBの追加を受け入れる。
システム書体だけで配信量を抑える案も比較したが、書体を揃える目的からフォールバックに留めた。

Chromiumの描画済みプローブ `日本語ABC 0O1l 髙﨑𠮷 🌸` をDevTools Protocolで確認した。
等幅案はOsaka-MonoとHiraKakuProN-W3、システム案はHiraKakuProN-W3、Noto案は
同梱のNotoSansJP-Regular（custom font）が使われ、絵文字はいずれもApple Color Emojiだった。
computed styleの候補名だけから実際の描画書体を断定していない。他2エンジンのOS書体内訳は未取得。

## 9. 実装後の検証と残件

- 3エンジンで通常モード時のフォント要求0件、フォーカス開始時に同一オリジンの固定URL1件を確認。本文に応じた外部通信はなかった
- 応答を保留している間も入力・削除・検索でき、成功／失敗後とも本文・選択・検索状態・同じtextarea DOMを維持した。書体swapで折り返し位置が変わっても現在一致は可視範囲へ戻った
- 320、480、767、768、960、1440、2560pxでtextareaと検索層の内幅・scrollHeightは一致。独立した文字組みDOMのRange計測との差はChromium約0.02px、Firefox約0.001px未満、WebKit約0.89px以内
- 本番ビルドのbase `/font-check/` で、フォントとライセンス全文を同じbase下から取得できた。通常のbaseでビルドし直した
- ローカルViteでResource Timingを1回ずつ取得：Chromiumは初回59.7ms、再訪1.2ms、WebKitは初回4ms、再訪1ms。再訪はいずれもbody転送0 bytes（304相当）。Firefoxは初回13ms、再訪のResource Timingエントリーなし。再訪時間や転送量を0と断定しない。これはlocalhostの資産取得時間であり、インターネットの速度やデコード・描画込みの体感時間ではない
- 読込完了・失敗時の検索位置と状態保持2件、通常モードの位置維持と破棄時のリスナー解除1件、計3件を追加
- lint、型チェック、ビルド、diffチェックは成功。全体テストは520件成功、既存のPR-3の2,000件ハイライトテスト1件が5秒でタイムアウト。licenses:checkは既存PR-2のbrace-expansion不整合（lock 2.1.4、installed 2.1.2）で失敗し、依存一覧の再生成は行っていない
- Chromium・WebKitのモード往復Undo/Redoを確認。Firefoxは変更前CSSでもモード切り替え後にUndoできない既存PR-4を再現。今回修正したとは扱わない

対象実装と利用可能な開発環境での検証を完了した。Windows、iPadOS、製品版ブラウザと最低対応版、
実際の200%ズーム、IME、低速な実回線は未確認。実機では書体・欠字・プレースホルダー・選択・検索・
モード往復・Undo/Redoをライト／ダークで確認する。No.3へ新機能実装を持ち越さず、
実機検証と既知問題はPR-2・PR-3・PR-4へ残す。次の改善対象はNo.3であり、今回着手していない。
