# No.6 タイプライターモード 設計書

作成日：2026-10-15／優先度：中／状態：PR-17の計測試作完了・全文ミラー方式不採用・本実装は保留

## 1. 目的と対象範囲

フォーカスモードで入力中の見た目の行を、編集可能領域の中央付近へ自動スクロールする。
既存のtextareaを維持し、通常モードの右ペイン同期とは独立して動作させる。
論理行数だけで位置を計算せず、日本語の折り返しを反映する。

## 2. 現状と仕様差分

- `useFocusMode.ts` がモード切り替え前の編集位置を取得し、描画後に復元する。
- フォーカス中はtextarea内部スクロールを強制する。
- `useScrollSync.ts` はフォーカス中に停止する。非表示DOMによる折り返し計測を持つ。
- `MarkdownEditor.vue` はIME、検索移動、入力支援による編集・選択更新を扱う。
- 現行仕様には自動的な中央追従とその設定はない。

入力支援の自動編集完了、検索移動、モード位置復元がスクロールを書き換えるため、
新機能側で優先順位と停止条件を明示する必要がある。

## 3. 操作・状態の推奨仕様

- 初期値はOFF。フォーカスモードのタブ名行の右端へ切り替えボタンを置く。
- 左上の「×」「？」は増やさず、タブ名は残り幅へ縮小・省略して重なりを避ける。
- ボタンは既存のIconButtonとAppIconの仕組みを利用し、`aria-pressed`、状態と操作を示す
  ラベル、共通ツールチップ、キーボードフォーカス表示を持つ。
- 常設の編集ツールバーや設定パネルは追加しない。狭い画面も同じボタンを利用する。
- ON/OFFは同じページの利用中だけ保持し、通常モードでは作用させない。再読込でOFFに戻る。
- 状態は `useFocusMode` で所有し、AppからMarkdownEditorへ渡す。LocalStorageとAppSettingsは変更しない。
- ON操作後はボタンにフォーカスを残す。textareaへフォーカスが戻り、選択範囲が閉じている場合に追従を開始する。
- モードへの再入場時は既存の位置復元を優先し、次の明示的な入力・カーソル操作まで追従しない。

永続化やタブごとの設定は対象外。初期OFF・ページ内保持は設計上の提案として仕様へ反映してから実装する。

## 4. 追従と停止の優先順位

| 操作・状態 | 挙動 |
| --- | --- |
| 入力、Enter、削除、貼り付け、入力支援、Undo/Redo | 編集と選択の更新完了後に1回追従 |
| 矢印・Home/End・PageUp/Down等のカーソル移動、本文クリック | 範囲選択がなければ移動後に追従 |
| Shift操作・ドラッグによる範囲選択 | 選択中は停止。選択と端点を変更しない |
| IME変換中 | 計測と自動スクロールを停止。確定後の既存入力置換・補正まで完了してから追従 |
| ホイール、タッチスクロール、スクロールバー操作 | 即時一時停止し、読む位置を維持 |
| 手動スクロール後の待機・本文値の外部更新 | タイマーでは再開しない |
| 手動スクロール後の次の入力・明示的カーソル移動 | 選択が閉じていれば再開 |
| 検索・置換UI表示中 | 自動追従を停止し、検索の現在一致への移動を優先 |
| 検索UIを閉じる | 閉じるだけでは再中央化せず、次の入力・カーソル操作で再開 |
| タブ名編集、解説やボタンへのフォーカス移動 | textareaにフォーカスがない間は停止 |
| モード終了・切り替え・位置復元中 | 予約フレームを破棄し、既存の位置復元を優先 |
| リサイズ、フォント読込完了 | 計測を無効化。追従中かつtextareaにフォーカスがある場合だけ再計測 |

自動スクロールが発生させるscrollは手動操作と扱わない。書き込み後の実scrollTopを記録し、
一致するイベントを除外する。意図を判定できないscrollは一時停止側へ倒し、追従の振動を避ける。
wheel/touch/pointerイベントは入力を妨げる `preventDefault` を行わない。

## 5. カーソル位置の計測とスクロール

1. textareaにフォーカスがあり、selectionStartとselectionEndが一致する場合だけ計測する。
2. `getComputedStyle` と `clientWidth` から本文の書体、サイズ、行高、字間、padding、
   white-space、tab-size、折り返し条件、実際のスクロールバーによる内幅を計測用DOMへ反映する。
3. 完全な原文のカーソル位置へ幅を持たない計測マーカーを置き、見た目の行の中央Yを得る。
   `textContent` とDOM APIだけを使い、原文をHTMLとして解釈しない。`aria-hidden`、非表示、
   pointer-events無効とし、textareaや検索層を計測用DOMで置き換えない。
4. 折り返し直前・直後、末尾改行、タブ、絵文字、連続空白を実ブラウザで比較する。
   マーカーによる折り返し差や行境界の曖昧さが解消できなければ、行数による近似へ逃げず方式を再検討する。
5. 通常はtextareaの表示高の50%を目標とする。ソフトウェアキーボードなどで表示域が狭くなる場合は、
   VisualViewportとtextareaの表示範囲の交差領域の中央を用いる。座標系を揃え、ページスクロールは変更しない。
6. `targetScrollTop = caretCenterY - targetY` とし、0から `scrollHeight - clientHeight` へ丸める。
   横方向のscrollLeft、選択、フォーカスは変更しない。
7. 誤差が行高の1/4以内なら書き込みを省略し、それ以外は即時移動する。smoothスクロールは使わない。
8. 変更後は既存の検索ハイライトscroll同期経路を利用する。

先頭付近の行はscrollTopが0より小さくできないため、中央にできない場合がある。
先頭に半画面の余白を加える方式は採用しない。最終行を中央へ寄せられるよう、ONの間だけ
textareaと検索層の下paddingを `max(既存値, clientHeight - targetY - 行高 / 2)` へ広げる。
原文に改行は追加しない。OFFや終了時に戻し、scrollTopが範囲外になればブラウザの丸めを許容する。
短文を含め「すべての行が常に中央」とは保証しない。

`MarkdownEditorViewState` の既存型を再利用し、独自の履歴や選択モデルを追加しない。
Parser、Converter、新規依存、保存スキーマは変更しない。

## 7. 性能とライフサイクル

- 更新・計測・スクロールはrequestAnimationFrameにまとめ、1フレームに複数の全文DOMを作らない。
- 本文、幅、文字組み、表示高さの変更で計測キャッシュを破棄する。不要なMarkdown再解析は行わない。
- OFF、モード終了、アンマウント時にフレーム、イベント、ResizeObserver、フォント監視、計測DOMを解除する。
- 日本語1万・5万文字を評価用入力とし、連続入力時の遅延と計測時間を実機で記録する。
  1回の計測が継続して16msを超える場合は、更新された論理行・カーソル周辺の再計測へ絞る方式を検討する。
- 遅延や計測不正時はそのフレームの追従を省略し、入力の完了を優先する。

## 8. 検証と受け入れ条件

- 単体テスト：座標の丸め、中央目標、手動停止と明示操作による再開、IME中停止、検索優先、
  予約フレームの破棄、連続イベントの集約を入出力と観測可能なscrollTopで検証する。
- 結合テスト：初期OFF、ON/OFF、モード往復・再読込、本文・選択・textarea DOM保持、
  通常モードと右ペイン同期への非干渉を確認する。共通化後は既存同期テストも通す。
- 実ブラウザ：Chrome、Edge、Firefox、Safari、iPadOS/iOS、Androidの対象環境で、
  日本語折り返し、行末、末尾改行、長いURL、コード、空文書、短文、長文、リサイズ、ズームを確認する。
- 実IMEで未確定文字・候補位置・確定後の補正・Undo/Redoを確認し、jsdomで確認済みとしない。
- 手動でスクロールして待っても戻らず、次の明示操作でだけ再開する。
- 中央化できる行は原則として中央から行高の1/4以内となり、振動せず、本文・横スクロールを変更しない。
- lint、型チェック、単体・結合テスト、ビルドを実行し、実機未確認範囲を記録する。

### 折り返し境界の不成立

本文を「文」100文字、本文幅720pxにすると、1行目末尾と2行目先頭のクリックはどちらも
selectionStart=selectionEnd=39となった。selectionDirectionも各エンジン内で同じ
（Chromium/WebKitはnone、Firefoxはforward）、scrollTopも0だった。
一方、Chromium・WebKitのネイティブキャレットはクリックした行に表示され、行中央Yは32.4px異なる。Firefoxはキャレットが画像に描画されず、見た目の行は未確認（点滅停止設定でも同様）。

| エンジン | 1行目末尾の赤いキャレット | 2行目先頭の赤いキャレット |
| --- | --- | --- |
| Chromium | [画像](assets/no-06-caret-chromium-end-of-first.png) | [画像](assets/no-06-caret-chromium-start-of-second.png) |
| Firefox | [撮影画像・キャレット未描画](assets/no-06-caret-firefox-end-of-first.png) | [撮影画像・キャレット未描画](assets/no-06-caret-firefox-start-of-second.png) |
| WebKit | [画像](assets/no-06-caret-webkit-end-of-first.png) | [画像](assets/no-06-caret-webkit-start-of-second.png) |

同じ原文・位置・方向・文字組みに対してゼロ幅マーカーから得られる座標は1つなので、
両方のキャレット行を行高1/4（8.1px）以内で再現できない。これは単なる計算誤差ではなく、
第5章の入力情報だけでは境界での表示行を特定できないという試作上の不足である。
クリック・カーソル操作履歴等による境界の扱いを追加検討する必要がある。

320/768/1440pxで空文書・日本語・句読点・タブ・連続空白・絵文字・URL・コード・表・末尾LFを確認。
マーカー挿入前後の全文高さ差は0だった。RangeとのY差はChromiumで0、Firefox/WebKitで
最大ほぼ1行。特に改行・境界でRange自体にも曖昧さがあるため、この差をそのままネイティブ
キャレット誤差とは扱わず、上のネイティブ画像を不成立の根拠とする。
空文書ではcollapsed Rangeの矩形を得られないケースもあった。

### 全文計測の性能

| エンジン | 1万文字 中央値 | 5万文字 中央値 | 5万文字 最大 |
| --- | ---: | ---: | ---: |
| Chromium | 2.8ms | 13.6ms | 22.2ms |
| Firefox | 2.0ms | 11.0ms | 12.0ms |
| WebKit | 12.0ms | 59.0ms | 62.0ms |

同じ日本語・英数字・LFの原文（正確に10,000/50,000コードポイント）を使い、末尾手前の
同じ位置で20回計測した。mirrorを再利用し、全文のTextNode置換と矩形取得に要する時間を測定。
computed styleの複製・mirror作成・Range比較・入力処理・解析・変換の時間は含めない。
実入力の遅延測定ではなく、開発環境での下限に近い試作値である。
WebKitは全20回で16msを超えており、第7章の条件に従って全文再計測方式を再検討する。

### 下余白と状態保持

- 元textareaを変更せず、非表示cloneで高さ753px・目標376.5px・下padding約360.3pxを試した
- 長文と末尾LFの最終行は、試作marker中央を基準に誤差0.5px以下で中央へ移動できた。ネイティブキャレット精度の合格を意味しない
- 空文書・短文の最終行はscrollTop=0で頭打ちとなり中央化できない。先頭余白を追加しない現設計の制約どおり
- 計測前後で元textarea DOM・値・選択・scrollTop・フォーカスを比較し、一致を確認。試作mirror/cloneはfinallyで除去する
- VisualViewport・ソフトウェアキーボード、連続入力・IME、検索優先・手動停止・予約フレーム破棄の製品接続試験は未実施
